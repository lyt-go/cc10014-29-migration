# 结构定义类型体系迁移与结构定义版本表 上线/回滚手册

## 1. 背景与问题根因

结构注册（`schema_registry`）与字段映射（`column_mapping`）历史上混用字符串类型简写
（`STRING`、`INT`、`BIGINT`、`TIMESTAMP` …），新规范要求落到带版本的类型
（`VARCHAR`、`INTEGER`、…）。两侧类型此前按字符串直接比较，一旦字段映射先切换到
新类型而结构表仍保留简写，同字段的 `STRING` 与 `VARCHAR` 会被持续判为不一致。

本次改造的根因修复：**类型比较只能经过 `app/type_catalog.py` 归一化，禁止字符串直比**。
旧 `STRING` 与新 `VARCHAR` 归一化后同属字符族，判定兼容，不再报错。

## 2. 类型别名注册表（`app/type_catalog.py`）

- `LEGACY_ALIASES`：旧简写（大小写、空格、`VARCHAR(255)` 长度声明均兼容）到规范类型的唯一映射；
- `TYPE_CATALOG_VERSION = type-v2`：类型体系自身版本，写入每一条版本表记录的「类型版本」；
- `COMPATIBILITY_FAMILIES`：同族兼容（字符族、整数族、数值族、时间族）；
- 无法识别的类型返回 `UNKNOWN`，保守判为不兼容并进入人工裁决，不静默放行。

## 3. 为什么旧类型映射与新类型版本必须一起迁移

版本表以「表 + 字段」为粒度，同时采集两个来源模块：

| 来源模块 | 类型字段 | 表名来源 |
| --- | --- | --- |
| `schema_registry` 结构定义 | 字段类型 | 记录自带「表名称」 |
| `column_mapping` 字段映射 | 数据类型 | 经「来源批次 → ODS 表名称」反查 |

同一迁移批次（`MG-*`）内，两侧片段同时落表，每行同时记录**旧类型写法、规范类型、
类型版本、旧别名标记、来源模块**。若只切一侧，版本表会缺失对照面，类型比较仍会报错；
因此接口层只暴露一个 `POST /api/schema_version/migrate`，不提供单侧迁移入口。

迁移幂等：以 `来源模块:记录id:字段:旧写法` 为指纹，重复发起只做增量补齐，不产生重复片段。

## 4. 超时即重试

- 版本表单点写入 `_write_version_row` 抛出 `SchemaVersionTimeout` 即视为超时；
- 每张表共享重试预算（默认首次 + 2 次重试，`max_retries` 可调，上限 5）；
- 超时后清掉该表本批已写片段再整体重试，避免半截数据；
- 重试预算耗尽：该表标记「迁移失败」，**其他表不受影响**；失败片段保留在版本表，
  下次发起迁移按指纹增量补齐。

## 5. 版本冲突的优先级（谁优先、哪个先处理）

同表同字段出现多种写法（典型：旧 `STRING` 与新 `VARCHAR` 存量冲突）时，按固定优先级裁决：

1. **模块优先**：结构注册 `schema_registry` 优先于字段映射 `column_mapping`（结构注册是结构定义权威入口）；
2. **状态优先**：已生效/已上线 优先于 待校验 优先于 草稿；
3. **版本优先**：定义版本号高者优先；
4. **先处理原则**：生效批次早、记录 id 小者先处理。

- 归一化后同族可兼容 → 标记「别名兼容」，自动采用优先来源的规范类型；
- 不可自动兼容（如 `STRING` vs `TIMESTAMP`）或含未知类型 → 标记「待裁决」，
  版本表行 `abnormal=true`，经 `POST /api/schema_version/conflicts/{id}/resolve` 人工裁决。

**冲突片段全部保留不合并删除**；`GET /api/schema_version/consolidated` 把同表同字段的
多个片段折叠成一行，用户始终只看到一份完整结构定义版本表。

## 6. 依赖、构建、流水线、环境、数据库兼容

### 6.1 依赖

- 后端**无新增第三方依赖**，`type_catalog.py` 与版本表服务仅用标准库；`requirements.txt`
  无需变更，现有锁定版本（FastAPI 0.163 / Pydantic 2.14 等）直接兼容。
- 前端无新增 npm 依赖，仅新增 `views/schema_version/` 页面与路由。
- 依赖升级若在后续窗口发生，须与类型体系版本（`TYPE_CATALOG_VERSION`）同步评审：
  类型别名表扩项时升 `type-vN`，新版本号随迁移结果落库，保证版本表能区分不同类型体系下的解析结果。

### 6.2 构建

- 后端：`pytest` 全量 47 项（含 `tests/test_schema_version_migration.py` 17 项）；
- 前端：`npm run build`（`vue-tsc --noEmit && vite build`）须零错误。
  本次顺带修复了 `ods_layer` 页面模板引用未定义变量的既有类型损坏，构建门禁现已恢复有效。

### 6.3 上线流水线

1. 后端镜像构建（`backend/Dockerfile` 不变）→ 跑 pytest 门禁；
2. 前端镜像构建 → `npm run build` 门禁；
3. 部署后端（滚动更新，无数据迁移脚本，版本表为应用内增量生成）；
4. 部署前端；
5. 上线后执行 `POST /api/schema_version/migrate` 生成结构定义版本表（只读扫描两个存量模块，不改写存量数据）；
6. 核对 `GET /api/schema_version/progress` 逐表进度与 `/conflicts` 冲突清单；
7. 确认无「待裁决」后执行 `POST /api/schema_version/switch` 发起统一切换批次。

### 6.4 环境

- 无新增环境变量；本地 `.env.example` 的 `APP_ENV=local` 与 compose 的
  `VITE_PROXY_TARGET` 约定不变。
- 当前实现为内存仓库（`app/store.py`），重启回到种子态；生产替换为数据库访问层时，
  本手册的批次/回滚语义保持不变（见 6.5）。

### 6.5 数据库兼容

- **只加表、不改表**：新增逻辑表 `schema_version`（版本片段）与
  `schema_version_batch`（迁移/切换批次与回滚点），存量 `schema_registry`、
  `column_mapping` 表结构不变；切换批次对存量类型的改写是等值 UPDATE，旧值已先写入回滚点快照。
- 字符集按现有库默认（UTF-8），新表字段长度按现有 `varchar` 表对齐即可；
- 迁移可重复执行、可增量补齐，不依赖专属 DDL 工具窗口。

## 7. 部署回滚

### 7.1 切换前的整批回滚点

`POST /api/schema_version/switch` 在改写前对结构定义、字段映射、版本表做深拷贝快照，
存入切换批次（`SW-*`）的「回滚点」，并在 `GET /api/schema_version/batches` 中显示「已保留」。

### 7.2 回滚方式

| 范围 | 接口 | 行为 |
| --- | --- | --- |
| 整批回滚 | `POST /api/schema_version/rollback?switch_batch=SW-xxx` | 两模块存量类型全部还原为切换前旧简写，批次置「已回滚」，版本表片段标「已回滚」 |
| 单表回滚 | 同上加 `&table_name=ods_orders` | 只还原该表相关的结构定义与字段映射行，其他表保持已切换 |

**任一范围的回滚都不删除版本表记录**：结构版本片段、冲突裁决、批次台账全部保留，
回滚后可重新切换，已迁移片段不丢失。

### 7.3 应用层回滚（镜像回退）

- 新版本仅新增模块与路由，回退旧镜像后旧接口行为不变；版本表两张新表可保留，
  旧版本不读取即无影响。
- 已执行切换批次的环境，先做 7.2 的数据回滚再回退镜像，避免旧镜像读到规范类型后
  按字符串直比再次误报。

## 8. 调用链与跨模块编排

```
原始入库确认 → 字段映射（数据类型，含规范数据类型解析）
            → ODS 建表
            → 结构注册（字段类型，含规范字段类型解析）
            → 结构定义版本表（两来源同批迁移、冲突裁决、切换/回滚）
```

- 字段映射类型核对：`GET /api/column_mapping/{id}/type_check`，委托结构注册沿
  「映射 → ODS 表 → 结构定义」逐字段归一化比较；
- 结构注册入口：`GET /api/schema_registry/table/{table}/types` 查看逐字段旧写法/规范类型；
  页面提供「结构定义版本表详情」跳转，符合「先访问结构注册入口，再到版本表详情页核对」的操作路径；
- 表级比对：`TableCompareService.compare_schema_types` 同步改用归一化比较，
  比对结果内嵌 `schema_type_check`。
